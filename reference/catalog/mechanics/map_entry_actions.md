# Map Entry Handshake and Player Actions (sit, direction, name, time)

Target client version: `PACKETVER = 20260219`. Citations are `$RATHENA_PATH/src/map/...`. Movement, pathfinding and AoI are in [movement_aoi.md](./movement_aoi.md). Opcode values here come from rAthena's default tables; for the 20260219 client-to-map opcodes, `clif_shuffle.hpp` overrides apply (see `packets/map.md`), and `packet_db[...].pos[]` offsets decide field positions.

## Map entry: CZ_ENTER (`clif_parse_WantToConnection`)

* Provenance: `clif.cpp:10643-10743`. Recorded only (auth is out of scope).
* Reads `account_id, char_id, login_id1 (auth code), client_tick, sex` from the frame. Rejects (`0x006a` with error code, then EOF) when `clif_parse_WantToConnection_sub` fails (invalid account/char/sex); `authfail 1` if server not running; `authfail 8` on double login / existing auth node mismatch (`node->account_id == account_id && char_id == char_id && state == ST_LOGIN` required).
* On accept: creates the session, sends `ZC_AID` (`0x0283`, `<aid>.L`) immediately, then `chrif_authreq` to char-server; the rest (`ZC_ACCEPT_ENTER`) is sent after auth succeeds.
* Login-time `0x0091` (source-derived; matches a real capture of the order `0x0283, 0x0b18, 0x02eb, 0x0201, 0x008e x2, 0x0091`; rAthena commit d4b8e7b). Sent by `pc_authok` (`pc.cpp:2080`, called from `chrif.cpp:702` when the char-server auth reply arrives), NOT by `pc_setpos`:
  * `pc_authok` calls `pc_setpos(last_point, CLR_OUTSIGHT)` (`pc.cpp:2226`). At that point `sd->prev == nullptr` and `state.active == 0` (`pc.cpp:1451`), so `pc_setpos` sends no `0x0091` and sets no `rewarp` (the `clif_changemap`/`rewarp` branch is `pc.cpp:7116-7120`); it only stores map/x/y.
  * Then `clif_inventory_expansion_info`, `clif_authok` (`0x02eb`), `clif_friendslist_send` (`0x0201`). Only if `!changing_mapservers` (i.e. a fresh login, not arrival from another map-server; `chrif.cpp:670`): optional version line (`display_version`, `0x008e`), MOTD lines (`0x008e`, or colored message), then an explicit `clif_changemap(sd->m, sd->x, sd->y)` = `0x0091` with the char's own map and cell (`pc.cpp:2254-2275`). Unconditional on first login (no other flag); skipped on cross-map-server arrival.
  * Source comment: "Fixes login-without-aura glitch (the screen won't blink at this point, don't worry)" (`pc.cpp:2270-2272`). So its purpose is a client-side visual-state refresh; the server does not wait for it or track it. Whether the 20260219 client strictly requires it to proceed is not determinable from source (the client later sends `0x007d` regardless); capture should decide.
  * Packets that appear after it in other logins (`ZC_PAR_CHANGE`, `0x0141`, `0x013a`, `0x09e7`, ...) come from the rest of `pc_authok` / `pc_reg_received` / `pc_scdata_received`-time status and inventory calc, not from the `0x0091` path.
* `ZC_AID` `0x0283` is sent from `clif_parse_WantToConnection`; `0x0b18` etc. are sent from `pc_authok`/`clif_authok` neighbours (not traced here).

## Map entry: CZ_NOTIFY_ACTORINIT (`clif_parse_LoadEndAck`)

> Open findings: [PF-12](../../../PACKET_FINDINGS.md#pf-12).

* Provenance: `clif.cpp:10748-11184`. Order of operations for the first login (`state.connect_new`) vs. map change:
  1. Guards: ignore if `sd->prev != nullptr` (already on the grid); if char not fully loaded, defer; `state.rewarp` -> re-send `clif_changemap` and return (`10752-10766`). `warping = 0`.
  2. Look/inventory: `clif_changelook(LOOK_WEAPON,0)` (goes to `AREA`, not only self: in the captures, observers already in view receive the newcomer's `0x01d7` (type 2, weapon id) just before its `0x09fe`; the frame is 15 bytes, see [PF-01](../../../PACKET_FINDINGS.md#pf-01)), costume view, clothcolor, `clif_inventorylist`, equip switch list, cart list if any, `clif_updatestatus(SP_WEIGHT)` and `SP_MAXWEIGHT` (these are `ZC_PAR_CHANGE` `0x00b0 <var>.W <value>.L`; `clif.cpp:3550-3558, 3639-3645`) (`10770-10794`). Var ids `SP_WEIGHT = 24`, `SP_MAXWEIGHT = 25`; values in 0.1 weight units (e.g. 20300 = 2030.0 max, 500 = 50.0), always `ZC_PAR_CHANGE` (never `ZC_LONGPAR_CHANGE`), weight first then max weight (frames 72-73 of [`login_sequence-rathena.txt`](../captures/login_sequence-rathena.txt)). Details: [map_units.md#0x00b0-zc_par_change](../packets/map_units.md#0x00b0-zc_par_change).
  3. Guild member info (before spawn so emblems show), `pc_setinvincibletimer`, map user counters (`10798-10813`).
  4. `map_addblock(sd)` (insert into 8x8 block grid; returns 1 on out-of-bounds -> abort) then `clif_spawn(sd)` (`10815-10817`). `clif_spawn` sends the spawn packet (`ZC_NOTIFY_NEWENTRY`-form via `clif_spawn_unit`, plus clothcolor and ball/status extras) to `AREA_WOS`, i.e. everyone within AREA_SIZE (14) EXCEPT the newcomer (`clif.cpp:1680-1740`).
  5. Party/BG hp, then `clif_map_property` (`MAPPROPERTY_NOTHING` for a plain map) to self (`10828-10846`).
  6. Nearby units to the newcomer: `map_foreachinallarea(clif_getareachar, m, x-AREA_SIZE, y-AREA_SIZE, x+AREA_SIZE, y+AREA_SIZE, BL_ALL, sd)` (`10850`). `clif_getareachar` skips the player itself, dispatches items/skill units to their own senders, others to `clif_getareachar_unit` (walking-entry form if the unit is mid-walk, else idle-entry `ZC_NOTIFY_STANDENTRY` form with `state = dead_sit`) (`clif.cpp:5574-5598, 5029-5066`).
  7. Pet, homunculus, mercenary, elemental: each `map_addblock` + `clif_spawn` + their info packets (`10853-10902`).
  8. First login only (`connect_new`, `10904-10988`): `clif_skillinfoblock`, hotkeys, `clif_updatestatus` for BASEEXP, NEXTBASEEXP, JOBEXP, NEXTJOBEXP, SKILLPOINT, then `clif_initialstatus` (`ZC_STATUS` plus `ZC_PAR_CHANGE` for STR/AGI/VIT/INT/DEX/LUK, ATTACKRANGE, ASPD and the renewal trait stats POW, STA, WIS, SPL, CON, CRT, PATK, SMATK, RES, MRES, HPLUS, CRATE, TRAITPOINT, AP, MAXAP, UPOW..UCRT; `clif.cpp:4123-4199`), riding/falcon status icons, friend list toggles, `NPCE_LOGIN` event, optional `clif_changed_dir` if `spawn_direction`.
  9. Map change (not first login): re-sends the six stats and renewal stats via `clif_updatestatus`, aborts scripts, partyinvitation state, config flags, reputation list, night effect, `status_calc_pc`, etc (`10989-11110`).
  10. Tail: guild notice, vending board, `NPCE_LOADMAP`, weather, NPC area touch check at spawn cell, death handling, `skill_unit_move`, `connect_new = 0`.
* `VAR_SPEED` (`SP_SPEED`, id 0) is NOT sent on a normal entry. It is sent only when `battle_status.speed` changes during `status_calc_pc` (`status.cpp:6594-6595`); the baseline is `DEFAULT_WALK_SPEED = 150` (`pc.cpp:1456`) so an unmodified character never triggers it. If the server wants the value, `clif_updatestatus(SP_SPEED)` = `ZC_PAR_CHANGE(var=0, value=speed)` (`clif.cpp:3646-3648`).
* First `0x007d` after login vs `rewarp` (source-derived, `clif.cpp:10748-10766`, `pc.cpp:2431,2494,14800-14806`): `rewarp` is NOT involved at login (it is 0, see `pc_setpos` above). The first `0x007d` can instead be swallowed by the "character loading not complete" guard: if `!state.active` (set in `pc_reg_received`, `pc.cpp:2431`) or `!state.pc_loaded` (set at the end of `pc_scdata_received`, `pc.cpp:14800`), `LoadEndAck` just sets `connect_new = 0` and returns with nothing sent. When loading finishes, `pc_reg_received` (`pc.cpp:2494`) and `pc_scdata_received` (`pc.cpp:14802`) see `connect_new == 0` and call `clif_parse_LoadEndAck` themselves, running the full entry burst without waiting for another client `0x007d`. A second client `0x007d` arriving later is a no-op (`sd->prev != nullptr` -> return, `clif.cpp:10752`). So the client sending `0x007d` twice is client behavior; the server tolerates both: early one swallowed (burst fires on load completion), late one ignored. Entry burst timing therefore may be driven by server-side load completion, not by the client's `0x007d`.
* Minimal subset an implementation needs for walking: `map_addblock`, spawn to others (AREA_WOS), nearby-units to self; everything else is feature content.

### Map change (same map-server)

Checked against real-client captures of rAthena `d4b8e7b` through `tools/proxy` (2026-10-23, two clients in a party). The captures are in the [captures appendix](../captures/README.md):
- [`packet_sequence-20261023_030246.txt`](../captures/packet_sequence-20261023_030246.txt): cross-map warps `prt_fild08` -> `prontera` -> `prt_fild08`, with an observer on `prt_fild08`;
- [`packet_sequence-20261023_031902.txt`](../captures/packet_sequence-20261023_031902.txt): `prt_fild08` -> `prontera`, an `@goto` jump (`0x0091` sent before the command's `0x008e` reply), then both clients walk into the same `prontera` -> `prt_in` (68,134) warp, the first one observed by the second;
- [`packet_sequence-20261023_032015.txt`](../captures/packet_sequence-20261023_032015.txt): same-map warps in `prt_in` (`prt20`/`prt20-1`), each client observing the other.

Warp-side details (trigger, destination cell, guards): [npcs.md#warp-trigger-for-the-warp-portal-feature](./npcs.md#warp-trigger-for-the-warp-portal-feature).

**What the captures show** (same-map and cross-map look identical on the wire):
- Self: `0x0091` with the destination `.gat` name and cell, and nothing else. No `ZC_STOPMOVE` for the cancelled walk, and no `0x0080` for the units that drop out of view.
- Observers in view at the source cell: `0x0080` type 0, in the same millisecond as the `0x0091`.
- Client: the next packet on the same socket is `0x007d`, 20 ms (small map, same map) to 630 ms (field) after the `0x0091`. It is followed at once by `0x0360` and later `0x08c9` and `0x0447`. The client sent nothing between `0x0091` and `0x007d` in any capture.
- Server reply to `0x007d` after a map change, in order: `0x01d7` (weapon look) -> `0x0b08`/`0x0b09`/`0x0b39`/`0x0b0b` (inventory) -> `0x0a9b` -> `0x00b0` WEIGHT, MAXWEIGHT -> `0x099b` `ZC_NOTIFY_MAPPROPERTY2` (payload `00 00 00 06 00 00`) -> entries for units in view (`0x09ff`/`0x09fd`, plus `0x0adf` after mobs and `0x080e` after party members) -> `0x0141` stat lines -> `0x02d9` x4 -> `0x0b8d` -> `0x0446` (quest NPCs, if any) -> `0x007f` (the reply to the client's `0x0360`). No `0x0283`, `0x0b18` or `0x02eb`.
- Observers in view at the destination cell get `0x01d7` and then `0x09fe` (`ZC_NOTIFY_NEWENTRY11`, spawn form) when the warping client's `0x007d` is processed, not when the `0x0091` is sent.

**Map property question (settled):** nothing is sent between `0x0091` and the client's `0x007d`. The client reloads and sends `0x007d` on its own. `0x099b` arrives inside the post-`0x007d` burst, in the same place as on first login. So a server whose first-login burst works without `0x099b` needs nothing extra for a map change. Whether the client needs `0x099b` at all is a separate question that these captures don't answer.

* Sequence (`pc.cpp:6930-7190`, `clif.cpp:2155`): trigger -> `pc_setpos` sets `state.warping = 1`, `state.changemap = true` -> `unit_remove_map_pc` (others: `0x0080` type 0; in-flight walk cancelled silently) -> `0x0091` to self -> sets `mapindex/m/x/y/ud.to_x/to_y` (and pet/homun/merc/elem coords) -> client loads -> `0x007d`. Nothing else is sent. `ZC_ACCEPT_ENTER` and `ZC_AID` are first-login only and are NOT re-sent.
* Packets between `0x0091` and `0x007d` (source only; the client sent none in the captures): dispatcher drops every packet except `clif_parse_LoadEndAck` while `sd->prev == nullptr` (`clif.cpp:25794-25796`). This covers moves, actions and chat.
* Flags while waiting: `prev == nullptr`, `warping = 1`, `changemap = true`; `rewarp` is 0 unless `pc_setpos` is called again while `prev == nullptr && state.active` (`pc.cpp:7119-7120`). In `LoadEndAck`: `prev != nullptr` -> return (duplicate `0x007d`); `rewarp` set -> clear, re-send `clif_changemap(sd->m, sd->x, sd->y)`, return, still waiting for the next `0x007d` (`clif.cpp:10752-10766`); otherwise `warping = 0` and the full sequence runs.
* Always runs (map change and first login): look/weapon, costume view, clothcolor, inventory list, equip-switch list, cart (if any), `SP_WEIGHT`/`SP_MAXWEIGHT`, guild member info (if any), `map_addblock` + `clif_spawn` (others only), party hp (if any), `clif_map_property`, `clif_getareachar` over the AoI, pet/homun/merc/elem spawns (if any), the six base stats (plus renewal trait stats) via `clif_updatestatus`, weather, arrival-cell NPC touch.
* Changemap-only (`state.changemap`, `clif.cpp` ~11000-11110): party-invite state, equipcheck, pet autofeed, `CONFIG_CALL`, `CONFIG_DISABLE_SHOWCOSTUMES`, reputation list, night flag, battleground/KS messages, `status_calc_pc`, map channel join, `clif_pk_mode_message`. Not needed by a minimal server.
* `connect_new`-only (first login): skill list, hotkeys, base/job exp and next-exp, skill points, `clif_initialstatus`, riding/falcon icons, friend toggles, `NPCE_LOGIN`.
* Map property: no code gates the loading screen on stats or inventory. The client signals that it has finished with its own `0x007d`. See "Map property question (settled)" above.
* Persistence: `pc_setpos` writes nothing to `status` and does not call `chrif_save` on a same-server change (only in-memory `mapindex/m/x/y`). `last_point` is derived from the current position inside `pc_makesavestatus` (`pc.cpp:1352`, `last_point` at ~1380-1427; falls back to `save_point` when jailed or for some map flags/instances), called by `chrif_save` (`chrif.cpp:282`). `chrif_save` runs from autosave (`pc_autosave`, `pc.cpp:13002`), logout (`chrif.cpp:520,752`), `@save`, trade/buyingstore, and cross-map-server moves (`pc.cpp:7072`). `save_point` changes only via save-point mechanics.

## Sit / stand: CZ_REQUEST_ACT (action 2 / 3)

* Provenance: `clif.cpp:11697-11830, 5329-5360`, `pc.hpp:1149,1151`, `pc.cpp:13099-13119`, `clif.hpp:691-695`.
* Packet field layout: `<target id>.L <action>.B`; action 0 attack, 1 pick up, 2 sit, 3 stand, 7 continuous attack (`clif.cpp:11807-11816`).
* Broadcast: `ZC_NOTIFY_ACT` (for PACKETVER >= 20131223 header `0x08c8`, 34 bytes: `packetType, srcID, targetID, serverTick, srcSpeed, dmgSpeed, damage(.L), isSPDamage(.B), div(.W), type(.B), damage2(.L)`; `packets.hpp:1412-1426`) with `srcID = unit id`, `type = DMG_SIT_DOWN (2)` / `DMG_STAND_UP (3)`, all other fields zero (`clif_sitting`/`clif_standing`, `clif.cpp:5329-5360`, enum `clif.hpp:691-695`). Target is `AREA`: all players within 14 cells INCLUDING the sitter. 
* Sit preconditions (`11740-11776`): basic-skill check (`basic_skill_check`), not already sitting, not casting, `opt1` clear (except stone-wait/burning), not dancing, not Gravitation self, not `PCBLOCK_SITSTAND`. Failures are silent `break` (or a skill-fail / blocked message).
* Sit effects: `pc_setsit` = `unit_stop_walking(USW_FIXPOS|USW_MOVE_FULL_CELL)`, `unit_stop_attack`, `state.dead_sit = vd.dead_sit = 2` (`pc.hpp:1149`). `pc_issit` is `vd.dead_sit == 2` (`pc.hpp:1151`).
* Sit while walking: before the switch, any action other than attack calls `unit_stop_walking(&sd, USW_FIXPOS)` (`11704-11709`): timer deleted, unit stays on its last COMPLETED cell, `ZC_STOPMOVE` (`0x0088`, `<aid>.L <x>.W <y>.W`) broadcast `AREA` incl. self (`unit.cpp:1695-1755`, `clif.cpp:2205-2213`), then sit proceeds. So the sequence is STOPMOVE then NOTIFY_ACT(sit). `clif_fixpos` is only reached if the unit was actually walking (`walktimer` set) since `USW_FORCE_STOP` is not passed (`unit.cpp:1711`); a standing player that sits gets no `0x0088`. Layout: [map_units.md#0x0088-zc_stopmove](../packets/map_units.md#0x0088-zc_stopmove).
* Repeated sit while sitting: "Bugged client? Just refresh them": re-broadcasts `clif_sitting` and returns (`11746-11750`). Repeated stand while standing: re-broadcasts `clif_standing` (`11778-11782`).
* Moving while sitting: `unit_can_move` is false for sitting players (`unit.cpp:1819`), so `CZ_REQUEST_MOVE` is silently ignored (no reply) after path search passes. 
* Stand: gated on `opt1` and `PCBLOCK_SITSTAND`; `pc_setstand(sd, false)` fails only with forced-sit statuses; it ends `SC_TENSIONRELAX`, calls `clif_standing` itself (`pc.cpp:13109`), clears `dead_sit`; then the parser calls `clif_standing` AGAIN (`clif.cpp:11800`), so rAthena emits the stand notify twice. A clean implementation can send it once.
* Entry packets: sitting state is carried in the idle-entry form (`ZC_NOTIFY_STANDENTRY`) field `state = vd->dead_sit` (`clif.cpp:1160`): 0 standing, 1 dead, 2 sitting. The new-entry (spawn) form and walking-entry form have no sit state field (`clif.cpp:1261-1330`), consistent with units being able to sit only when standing still.

## Direction change: CZ_CHANGE_DIRECTION

* Provenance: `clif.cpp:11565-11620`, `pc.hpp:499,1170`, `unit.hpp:49`.
* Frame: `<head dir>.W <dir>.B` (0x0361 = 5 bytes in packet table; head dir is read as a single byte at `pos[0]`, dir at `pos[1]`; `clif.cpp:11611-11617`).
* `pc_setdir(sd, dir, headdir)` is a bare macro `ud.dir = dir; head_dir = headdir` with NO validation (`pc.hpp:1170`). Documented ranges: body `dir` 0..7 (0 N, 1 NW, 2 W, 3 SW, 4 S, 5 SE, 6 E, 7 NE; `clif.cpp:11565-11580`), `head_dir` 0 straight, 1 turned CW, 2 turned CCW (`clif.cpp:11567-11570`; `pc.hpp:499` says right/left). A Rust server should validate (`dir < 8`, `head_dir <= 2`) and drop the session or ignore on violation; rAthena would store and broadcast garbage (and index `dirx[]` out of range later).
* Broadcast: `clif_changed_dir(*sd, AREA_WOS)`: recipients are everyone in the 29x29 AoI EXCEPT the sender. Packet `ZC_CHANGE_DIRECTION` `0x009c`: `<srcId>.L <headDir>.W <dir>.B`, with head dir 0 for non-players (`clif.cpp:11581-11594`, header `packets.hpp:694`).
* Walking resets `head_dir` to 0 at walk start (`unit.cpp:299-302`).

## Name request: CZ_REQNAME

* Provenance: `clif.cpp:11467-11505`, `packets_struct.hpp:3562-3583`, `clif.cpp:9928-9960`.
* Frame `<id>.L`. Lookup `map_id2bl(id)`; unknown id -> silent return. Negative id equal to `-sd->id` is the disguise self-lookup.
* Range check: `sd->m != bl->m || !check_distance_bl(sd, bl, AREA_SIZE)` -> silent drop (Chebyshev 14).
* Reply: `clif_name(sd, bl, SELF)` to the requester only. For a player target: `ZC_ACK_REQNAMEALL` (PACKETVER >= 20150225/RE 20141126 -> opcode `0x0a30`: `<gid>.L name[24] party_name[24] guild_name[24] position_name[24] title_id.L`; older `0x0195` without title; both with fixed 24-byte NUL-padded strings, empty strings when no party/guild). Party name is only shown together with a guild. NPC targets get `0x0adf` (58 bytes, see [map_units.md](../packets/map_units.md#0x0adf-zc_ack_reqnameall_npc-reply-to-cz_reqname-for-an-npc)); mob targets get `0x0adf` too unless `show_mob_info`/guardian.

## Time sync: CZ_REQUEST_TIME

* Provenance: `clif.cpp:11187-11209`, `packets.hpp:2011`.
* Frame `<client tick>.L`; stored into `sd->client_tick` (no validation). Reply `ZC_NOTIFY_TIME` `0x007f` `<time>.L` with `client_tick(gettick())`: the server's monotonic millisecond tick (the same time base as `moveStartTime` in `ZC_NOTIFY_PLAYERMOVE` and `ZC_ACCEPT_ENTER`). Self only. The client tick is NOT echoed back.

## Client input unblock / account settings (`0x0447` -> `0x0b1b`)

> Status: the handshake is settled; what the first load waits for is not (see Inference). Web search found nothing on this (2026-10-24).

* Provenance (applies to `20260219`): `clif.cpp:20000-20022` (`clif_loadConfirm`, `clif_parse_blocking_playcancel`), `clif.cpp:24272-24295` (`clif_reputation_list`, gated `PACKETVER_RE_NUM >= 20211103 || PACKETVER_MAIN_NUM >= 20220330`), `packets.hpp:250-261`, `packets_struct.hpp:4029-4032`, `clif_packetdb.hpp:1244,1607`.
* `0x0447` `CZ_BLOCKING_PLAY_CANCEL`: 2 bytes, client to map, client-initiated. rAthena replies `clif_loadConfirm` = `0x0b1b` `ZC_NOTIFY_ACTORINIT` (2 bytes, no payload; `PACKETVER_MAIN_NUM >= 20190403`), then `clif_specialpopup` only if the map has `MF_SPECIALPOPUP`. rust-ro does the same (`server/src/server/request_handler/char.rs` `handle_blocking_play_cancel`, `mod.rs:142`); it has no code that triggers it.
* `0x0b8d` `ZC_REPUTE_INFO`: `<id>.W <len>.W <success>.B { <type>.Q <points>.q }*`; rAthena sends `success=1` and one entry per `db/re/reputation.yml` row (4 rows: Orc Village 1, Goblin Village 2, Grey Wolf Village 3, Isgard 4; points = char/account var, 0 default), so 5 + 4*16 = 69 bytes (matches the capture). Sent from `clif_parse_LoadEndAck` in the `state.changemap` block, which also covers first login (`0x02c9`, `0x02d9` x4 precede it in the captures).
* Capture correlation, every `0x0447` that follows a login or cross-map load: the client sends it 2-300 ms AFTER the server's `0x0b8d` and the preceding burst, and always after the `0x007d` reply (numbers below are proxy `#` sequence numbers, file line = `#` + 10, unless marked as file lines):
  * First login: `packet_rathena_item_2026-10-24.txt` lines 97 (`0x0b8d`) -> 103 (`0x0447`) -> 104 (`0x0b1b`); `login_sequence-rathena.txt` 102 -> 108 -> 109; `packet_sequence-20261023_030246.txt` 94 -> 95 -> 96.
  * Cross-map warps (no `0x010f`, no hotkeys, no skill list; only the changemap content incl. `0x02d9` x4 and `0x0b8d`): same file 139 -> 142 -> 143 and 170 -> 172 -> 173; `item_drop_pickup_sequence.txt` 94/98, 213/222, 311/314, 338/341, 745/747, 776/778.
  * **Same-map warps send none of the settings packets** (no `0x02c9`/`0x02da`/`0x02d9`/`0x0b8d`; `changemap` is false) and the client still sends `0x0447`: `packet_sequence-20261023_032015.txt` file lines 244-262, 272-297, 306-324 (burst = inventory, weight, `0x099b`, entries, `0x0141`, `0x0446`, `0x007f`, then `0x0447` ~280 ms later). So `0x0b8d` is NOT a per-load trigger.
  * metaling `metaling-20261024.txt`: no `0x0b8d` (nor `0x02d9`, `0x02c9`, hotkeys, `0x010f`), no `0x0447` in the whole session (26 s), but the client still walks (`0x035f`) and sends `0x0b1c` pings.
